# 全界面 GUI 精简与渐进披露审计

- 日期：2026-08-05
- 状态：已转化为正式 PRD
- 下游落地：
  - [PRD 020](../prd/020-gui-simplification-and-progressive-disclosure.md)

## 结论

对 `Soma/Views`（约 14,400 行、24 个文件）与 `Soma/Components` 逐屏审计后，
“GUI 太重”的根源不是功能太多，而是三个系统性问题：

1. **平铺代替分层**：详情页把“看 / 改 / AI / 媒体 / 历史 / 管理”全部平铺在一屏。
   动作详情最多 7 个 Form Section；训练记录编辑约 12 个固定可编辑字段外加每组 2 个输入；
   训练计划详情纵向堆叠 6 大区块。
2. **低频功能占据主路径**：AI 优化、录像选项、远程执行切换、版本历史、合并归档等
   低频能力与核心 CTA 并列展示，违反“低频调试开关不得占用聊天主界面”的既有契约精神。
3. **视觉语言碎片化**：`DesignSystem` 采用率低。Views 中约 264 处硬编码 `.font`、
   233 处 `.foregroundStyle`，圆角出现 13 种数值；带练流自成一套绿色视觉语言。

**简化总策略：渐进披露（progressive disclosure）。** 默认只读或只显示核心信息，
编辑与低频操作经显式入口进入；不删除任何 PRD 授权的能力，只改变入口层级。

本调研的全部 P0/P1/P2 建议已被维护者采纳（2026-08-05），转化为 PRD 020。

## 逐屏审计与已采纳建议

影响面标注：**视觉** = 布局/文案/默认显隐；**交互** = 导航、折叠、菜单、渐进展示；
**数据** = 需要触碰查询、字段读写策略或计算规则（本次全部避免）。

### 6. 横切：设计系统收口

- `DesignSystem` 主要服务「进展/设置」卡片流，Form 型页面（动作库、编辑器、带练）几乎未用。
- 已采纳（P2，随各批次重构顺带做，不做全仓一次性迁移）：
  - `DesignSystem.swift` 补充列表缩略图尺寸、统一圆角 token、次要操作菜单约定；
  - 本次重构涉及的 `ExerciseViews`、`GuidedWorkout*`、`TrainingProgramEditorViews`
    顺带替换硬编码字体/颜色/圆角为 `AppTheme` token。

## 红线：明确不动的核心能力

1. 聊天发送链路：文本/附件/语音/健身房切换（≥2 时）/附件预览。
2. 所有记录的 CRUD 能力：折叠不等于删除，字段仍可编辑、可保存、可左滑删除。
3. missing-is-nil：不为“表单变简单”增加必填校验或默认值回填。
4. API Key 配置、HealthKit 导入、导出/备份/清除、位置授权、远程明确授权披露。
5. 带练状态机行为语义不变，只调整呈现层级。
6. 高级设置中已正确下沉的演示切换、提示词、Skills、执行日志不回迁、不删除。
7. Tool Schema、Trace Event、外部导入幂等等系统边界不受影响。

## 实施切分

按界面域分 6 个批次落地（教练 → 训练 → 进展 → 设置 → 动作库 → 设计系统横切），
每批一个逻辑提交并通过 `make check`；全部完成后 `make verify` 并更新
`CHANGELOG.md` 与 `docs/acceptance.md`。正式范围与验收边界见
[PRD 020](../prd/020-gui-simplification-and-progressive-disclosure.md)。
