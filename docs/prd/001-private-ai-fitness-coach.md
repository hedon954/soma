# PRD 001：私人 AI 健身教练基础

- 状态：已演进，核心需求保留
- 决策阶段：2026-07-27
- 后续文档：[PRD 002](002-chat-first-review-loop.md)、
  [PRD 004](004-soma-current-product.md)

## 背景

用户需要的不是公开社区、课程商城或账号体系，而是一款只服务于个人的 iOS AI 健身教练。它需要理解用户拥有什么器械、吃了什么、身体如何变化、训练做了什么，并把这些信息放在同一个长期上下文里给出建议。

## 用户故事

### 1. 电子健身房

用户可以拥有多个健身房，并指定其中一个为当前健身房。用户拍摄器械和环境后，App 使用多模态模型识别：

- 健身房环境；
- 可见器械；
- 每件器械支持的训练类型与动作；
- 与训练有关的空间或安全信息。

电子健身房用于约束后续动作推荐，避免建议用户无法执行的动作。

### 2. 饮食记录

用户可以发送食物照片或文字。AI 识别食物、份量、估算热量与宏量营养，并保存为可统计的饮食记录。

### 3. 身体记录

用户可以发送体重秤、体型或体态照片，也可以直接描述体重、体脂或腰围。App 保存数值、原始描述、图片与非诊断性的 AI 观察，形成可回溯的身体历史。

### 4. 训练记录与 AI 教练

用户通过文字、图片或视频记录动作、组数、次数、重量、间歇和时长。对于媒体，AI 可以在证据充分时分析：

- 动作是否标准；
- 用户是否适合继续该动作；
- 负荷是否明显过轻或过重；
- 需要优先修正的动作线索；
- 应停止训练并寻求专业帮助的风险信号。

AI 教练结合训练、饮食、身体与当前健身房，提供训练、恢复和饮食建议。

### 5. 私有与本地

- 不需要账户、登录、社交或排行榜。
- 结构化数据和原始媒体保存在 App 沙盒。
- 只有用户主动发送时，当前消息所需的压缩图片、视频或关键帧才发送给所选供应商。
- API Key 保存在本机 Keychain。

### 6. 数据分析

统计界面采用克制、接近 Apple 原生应用的视觉语言，并借鉴 GitHub contribution graph 表达训练连续性。核心统计包括训练频率、体重变化、训练容量与近期记录。

## 初始产品范围

最初设想包含“今日、健身房、记录、数据、教练”等多个独立入口，以及训练、饮食、身体三类手动新增流程。这一信息架构随后被否决：它虽然覆盖功能，却仍然是传统数据库 App 的操作方式，不符合“AI 自动理解并记录”的产品定位。

## 保留的验收原则

1. 多个健身房必须共存，且只能有一个当前健身房。
2. 所有媒体必须能在记录详情中回看，不能分析后丢失。
3. AI 输出必须转化为可统计、可审查的数据。
4. 健身建议不得冒充医疗诊断。
5. 原“无 API Key 本地演示分析器”已由
   [ADR 0027](../adr/0027-required-ai-configuration-and-send-gate.md) 替代；演示记录仍可离线
   审查，但新聊天必须先配置标准档 API Key。
