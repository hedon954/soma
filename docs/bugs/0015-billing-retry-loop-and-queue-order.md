# BUG 0015：明确欠费在进入 App 后反复重试并可能破坏消息顺序

- 状态：已修复，待维护者真机确认欠费文案与队列交互
- 发现日期：2026-08-13
- 影响范围：Agent Job 恢复、聊天队列、供应商额度与用户信任
- 上游依据：无
- 下游落地：[PRD 027](../prd/027-reliable-efficient-react-and-in-context-review.md)

## 症状

供应商明确返回额度、账单或付款失败后，App 再次启动或回到前台仍会领取同一消息并请求模型。
如果后发消息绕过失败消息执行，聊天回复和结构化写入还会与用户发送顺序不一致。

## 根因

旧暂存策略把欠费与普通网络、限流和服务端故障都视为“稍后自动恢复”，没有持久的人工恢复状态，
队列领取也没有把最早的不可运行 Job 当成严格 FIFO 屏障。

## 修复

- 明确欠费进入非终态、不可运行的 `waitingForUser`，启动、前台、定时器和配置变化均不释放。
- 后发消息全部进入 `staged`，`claimNext` 不跳过最早屏障。
- 用户从完整暂存列表审查内容，只能通过按顺序重试全部、单条删除或清空队列推进；删除同步清理
  该 Turn 的本地投影与私有媒体。
- 普通网络和通用 429 保留原有可恢复暂存语义。

## 回归门禁

- `LLMOutageStagingTests` 覆盖欠费分类、人工释放、按顺序重试全部、FIFO、单删与全清。
- 手工验收使用虚构消息和测试 Provider：欠费后重启 App 不应产生新请求，发送两条新消息后顺序不变。

## 验证

- `make verify` 必须通过；真机仅确认文案、按钮可发现性与重启行为，不使用真实健康数据。
