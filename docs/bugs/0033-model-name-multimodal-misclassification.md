# BUG 0033：按模型名硬编码多模态能力导致误判

- 状态：已修复，待真实供应商目录验收
- 发现日期：2026-08-23
- 影响范围：LLM 配置、媒体发送门禁、本地与远程直传视频
- 下游落地：[ADR 0096](../adr/0096-source-backed-model-multimodal-capabilities.md)

## 症状

DeepSeek 配置为 `deepseek-v4-flash-vision-exp` 时，Soma 显示“不支持多模态：只能发送文字”。同类
逻辑还按 Qwen 模型名前缀开启直传视频。两者都没有来自当前平台模型目录的能力证据。

## 根因

`ModelCapability` 同时使用 provider 分支、模型名包含关系和固定前缀清单，把命名约定当成能力事实。
这会让新模型、私有部署、实验模型和代理重命名产生假阳性或假阴性。

## 修复

- 模型名与 provider 始终返回未知；只解析当前 `/models` 条目的明确输入模态或视觉能力字段。
- 配置页同时显示判定和字段来源；缺来源显示未知，并允许真实请求验证。
- 本地直传视频只接受明确 `video` 输入元数据；远程直传视频只接受显式部署开关，默认关闭。
- 能力证据按 provider、Base URL、模型缓存，刷新目录后更新。

## 回归门禁

- 单元测试覆盖带 `vision` / `vl` 的多平台模型名仍为未知。
- 模型目录 fixture 覆盖明确支持、明确不支持和未知，并断言来源字段。
- Server 测试覆盖显式能力开关；静态检查禁止恢复模型名前缀能力表。

## 本轮验证

- iPhone 17 Pro（iOS 26.5）模拟器将 DeepSeek 模型填写为
  `deepseek-v4-flash-vision-exp` 后，界面显示“多模态能力未知”和“平台未提供能力信息”，不再
  显示“不支持”。
- `make verify` 通过；Server 直传视频测试只通过显式能力参数开启，不依赖测试模型名称。
