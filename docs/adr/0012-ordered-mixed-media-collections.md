# ADR 0012：有序混合媒体作为一等数据

- 状态：已采纳
- 决策阶段：2026-07-29

## 背景

早期记录只保存一个 `mediaKind` 和一个 `mediaPath`。这无法表达一次发送多张照片、
多个视频或二者混合的真实输入，也会让聊天、Agent 分析、业务记录和详情回看各自保留
不同的媒体子集。

## 决策

- 单条聊天消息最多接收十项有序媒体，照片和视频可以混合选择。
- `CoachMessage`、`WorkoutEntry`、`MealEntry` 和 `BodyEntry` 都保存完整的
  `MediaAttachmentReference` 集合。
- 集合以 Codable 数据保存在 SwiftData；旧的单媒体字段继续作为兼容入口，读取旧数据时
  自动合成为单项集合，新写入同时维护首项字段。
- Agent 对全部附件建立统一输入，视频在本机抽取代表帧；Trace 分别记录附件数量与实际分析
  帧数，但不保存媒体 Base64。
- 聊天中两项以内直接展示，三项起采用牌组折叠：第一张在前，并按其横向、方形或纵向方向
  选择稳定卡片画布；后图填充同一画布后再缩小、旋转并向右露出。折叠态优先保证聊天节奏，
  展开态再恢复每项媒体自身比例。
- 点击牌组后改为右对齐的竖直列表，再次点击收起；不提供横向滑动。
- 训练、饮食和身体详情展示完整媒体集合，而不是只展示首项。

## 未选择的方案

- 每条消息只保留首张图：实现简单，但丢失用户证据。
- 把每个附件拆成独立聊天消息：破坏一次输入对应一次 Agent Trace 的语义。
- 使用横向轮播作为聊天折叠态：浏览方便，但不符合低干扰的微信式展开交互。
- 让首图原始比例决定整个牌组尺寸：证据保真，但极端竖图会让单条消息过高，连续对话节奏
  不稳定。
- 直接删除旧单媒体字段：会让已有本地记录失去兼容读取路径。

## 结果

聊天输入、Agent、Trace、业务记录和审查详情共享同一份有序媒体事实。后续新增媒体能力必须
保持顺序、旧数据兼容和本地文件隐私，不能在不同层再次退化为“只取第一项”。
