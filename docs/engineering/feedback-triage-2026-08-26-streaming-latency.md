## 匿名化诉求

用户希望在流式回复体验明显过慢时，能够自动提交一份诊断性反馈，帮助维护者定位问题。

## 现有实现核对

当前自动邮件仅适用于系统 MetricKit 明确确认的崩溃；启动哨兵、强杀、模拟器停止或安装替换都不
能触发。逐回复产品反馈则由用户主动发送，并只在发送时组装当前 Turn 的有界脱敏上下文。

流式性能已有 UI、单元和 Release 真机验收路径，但“过慢”不是已定义的产品事件。一次较长的媒体
推理、没有首增量、文本投影卡顿和完成态布局变慢，也需要不同的观测指标和恢复方式。

## 为什么本轮不实施

自动提交会新增网络出站时机，且可能把对话、媒体、身体数据或 Trace 关联到性能事件。反馈没有
定义阈值、用户同意方式、可发送字段、留存/重试和失败后的可见恢复，因此不能把现有崩溃自动发送
机制泛化为性能上报，也不能把“慢”静默解释为某个供应商或模型故障。

本轮没有修改 App、Server、邮件配置、测试夹具、PRD、ADR 或 Changelog。

## 进入实现前的决策清单

维护者需先批准一份 PRD 和 ADR，至少明确：

1. 触发语义：分别界定首增量超时、持续投影延迟、完成态卡顿和用户主动取消；按文字、图片、视频
   任务分别评估，不能用单一“卡”阈值覆盖所有情形。
2. 授权与界面：是否默认关闭、如何一次性说明和撤回、自动提交前是否给用户可见提示，以及发送失败
   后如何由用户恢复。
3. 最小载荷：只允许经审查的性能计数或分桶时长、App/系统版本和匿名事件类别；明确禁止消息正文、
   原始媒体、身体/健康记录、位置、邮件地址、凭据、Authorization、模型输入输出、完整 Trace、
   稳定业务 ID 与日志尾部。
4. 本机留存与投递：本机队列上限、过期删除、去重键、网络条件、重试上限和不出网时的诊断可见性。
5. 验收：以虚构内容验证同意、拒绝、撤回、字段白名单、失败保留与重试；性能有效性仍以 Release
   真机 Time Profiler、SwiftUI 和 Animation Hitches 证据分级，不能只凭自动报告宣称性能达标。

## 后续建议

在上述决策完成前，继续使用现有的用户主动逐回复反馈和受控性能录制。若批准自动性能诊断，应作为
独立的隐私与分发边界变更实施，不复用或放宽崩溃报告的自动触发条件。
