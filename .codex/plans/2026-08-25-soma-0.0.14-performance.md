# Soma 0.0.14 流式、进展与数据库性能计划

- 日期：2026-08-25
- 基线：`0.0.13 (17)` 源码基线 `b17d214`
- 上游依据：[ADR 0097](../../docs/archive/0.0.12/adr/0097-current-baseline-performance-budget-and-cache-invalidation.md)、
  [0.0.12 性能收尾复盘](../../docs/engineering/performance-optimization-retrospective-2026-08-25.md)
- 当前阶段：代码审计完成；动态归因和 0.0.14 实施待开始

## 1. 本轮结论

### 1.1 流式后半程和完成后的卡顿

当前实现已经做对三件事：

1. 文本 delta 只进入瞬态 `LiveAgentTextBuffer`，不在每个 delta 修改 SwiftData。
2. UI 更新约 5 Hz，自动滚底也限制为约 5 Hz。
3. 已冻结流式块使用稳定 ID、`Equatable` 子 View 和 `LazyVStack`。

但仍有两个代码级缺口：

1. `LiveAgentTextBuffer.defaultTargetCharacterCount = 256` 不是硬上限。`append` 只有在本次 delta
   含换行时才尝试冻结；一条很长但没有换行的段落会一直留在同一个可变 `Text`，每次 delta 都可能
   重新断行整段正文。这直接违背 ADR 0097 的「最多 256 字符可变尾块」。现有单测还把“无换行长段落
   保持单块”固定成了期望行为。
2. 流式完成会在一次状态更新中把稳定纯文本块替换成完成态 `CoachResponseView`。缓存 miss 时，完整
   Markdown 文档和每个 block 的内联 `AttributedString` 都在 `@MainActor` 同步解析；完成态内部使用
   `VStack`，会一次创建整条回复的全部 block。外层消息列表即使是 lazy，也无法让单条消息内部的
   eager 子树变 lazy。这是明显的“完成时性能悬崖”，也会让完成后的大视图继续驻留在 Coach Tab。

现有长流 fixture 每个 delta 都带换行，而且永远不发出完成事件、不落盘、不切换到 Markdown，因而
只能证明「有换行的流式稳态」，没有覆盖用户报告的两条路径。上述机制是 code-backed；它们在真实
回复中各占多少 CPU、布局和内存，仍需 Release 真机 trace 后才能写成 trace-backed 根因。

### 1.2 「进展」并不是列表懒加载失败

`InsightsView` 的内容确实放在 `LazyVStack` 中，但业务数据不是按滚动懒加载，而是由后台
`InsightsSnapshotLoader` 一次加载一个有上限的 95 天快照。空页面问题来自快照状态机：

1. 初次加载用 `try?` 吞掉所有错误；失败后只把 `requestedCacheKey` 清空，没有错误 UI，也没有重新
   发起请求。页面可以永久保留 `.empty`，直到 View 生命周期因切 Tab 等行为重新触发 `.task`。
2. 加载期间收到相关保存通知时只增加 `dataRevision`，不会排队新请求；旧请求成功后仍把旧 key 写入
   `loadedKey`，也不比较最新 key。首次空快照与新数据保存发生竞态时，旧空结果会被当作已完成结果。
3. 保存通知限定 `object: modelContext`。如果后续业务写入来自同一 container 的其他 `ModelContext`，
   当前页面不会收到失效信号。0.0.14 需要把 container 级失效纳入测试，而不是依赖当前写入恰好都走
   main context。

因此这是可复现的缓存失效与错误恢复 bug，不应通过反复刷新 Tab 规避。

### 1.3 SwiftData 索引现状

静态盘点结果：

- 28 个 `@Model`。
- 8 个 `@Attribute(.unique)`：mutation receipt key、compaction sessionKey、Workout 投影 key、
  Agent Job client key、Agent Event 拼接 key、动作 canonical name、迁移 marker、业务 ID namespace。
- 0 个 `#Index` / `#Unique` 复合声明。
- 业务 `id: UUID` 与多数 `businessID` 是普通持久字段，不是 SwiftData 内部 persistent identifier，
  也没有声明唯一或显式索引。

所以「没有面向热查询的显式索引」成立，但「完全没有索引」不成立：SwiftData 内部身份和八个唯一
约束仍有索引语义。

高频且应进入索引候选集的查询组合如下。最终只保留在压力数据上有收益的索引，不能把候选表直接
当成 migration 清单。

| 模型 | 当前热查询 | 候选索引 |
| --- | --- | --- |
| `CoachMessage` | `sessionID` 过滤、`date` 倒序分页；`id` / `turnID` 点查 | `(sessionID, date)`；经测量后评估 `id`、`turnID` |
| `ConversationSession` | `updatedAt` 会话列表；`startedAt` 今日会话；`id` 点查 | `updatedAt`、`startedAt`；经测量后评估 `id` |
| `WorkoutEntry` / `MealEntry` / `BodyEntry` | 日期窗口与倒序分页；`id` / `businessID` 更新 | `date`；经测量后评估 `id`、`businessID` |
| `ExercisePerformance` | `sessionID` + `order` | `(sessionID, order)` |
| `WorkoutSet` | `performanceID` + `order` | `(performanceID, order)` |
| `WorkoutEffort` | `workoutSetID` + `order` | `(workoutSetID, order)` |
| `PersistentAgentEvent` | `jobID` + `sequence` 增量 | `(jobID, sequence)`，不要只依赖拼接字符串 unique key |
| `AgentJob` | data space + state + FIFO；session / turn 点查 | `(dataSpaceRaw, stateRaw, createdAt)`；按实测评估 session / turn |
| `GymEquipment` / `GymMedia` | `gymID` | `gymID` |
| HealthKit / cursor | source + external ID 去重；source + stream cursor | 复合身份；需要同时审查唯一性语义 |

不能在 0.0.14 直接无条件加入 `#Index`：项目 deployment target 是 iOS 17，而当前 SDK 将 `#Index`
标记为 iOS 18+。提升最低系统版本是长期产品决策，需新增 ADR；保持 iOS 17 时不允许直接修改
SwiftData 私有 SQLite schema。索引实施前必须明确选择：

- 路径 A：继续支持 iOS 17，先完成查询收窄、分页和快照修复，用真机数据判断剩余瓶颈。
- 路径 B：最低系统提升至 iOS 18，新增 ADR，再用 `#Index` 和必要的 `#Unique`，并验证现有 store
  打开、演示/个人空间、备份恢复及查询计划。

默认采用路径 A，除非维护者明确接受最低系统版本变化。

### 1.4 查询本身的 anti-pattern

索引之前必须先修查询，否则索引无法挽救无谓的数据物化：

1. `AgentBusinessKeyDeduper` 为一次同日去重分别加载全部 Workout、Meal、Body，再在 Swift 里按日期、
   来源和业务字段过滤。应先用日期窗口和可表达的业务字段下推 predicate，只对少量候选计算 fingerprint。
2. 本地 `AgentJobStore.claimNext` 先按 `createdAt` 读取整张 Job 表，再在 Swift 中找 data space、非终态、
   runnable 和 retry 时间。应把可表达条件下推，保持既有严格 FIFO 语义，并用小上限读取候选。
3. HealthKit 导入会加载某 source 的全部 Workout / Body external ID。应按本批变更 ID 定向查询，或维护
   有唯一语义的 source + external ID 身份，避免历史规模线性增长。
4. 多处 UUID / businessID 点查已有 `fetchLimit = 1`，但没有显式索引时仍可能扫描；`fetchLimit` 只限制
   返回量，不自动让过滤变成索引查找。

### 1.5 PostgreSQL

服务端核心约束和热路径已有索引：Job 主键、device + client job 唯一键、worker / retention、Event 的
job + sequence 唯一键、Tool 的 job + tool call 唯一键、upload、outbox partial index 等。

需要复核或补齐：

- `agent_events_cursor_idx(job_id, sequence)` 与同列唯一约束自动产生的唯一索引重复，应通过新的向前
  migration 删除冗余索引。
- cleanup 的 `request_nonces.expires_at`、`device_registration_challenges.expires_at`、
  `devices.revoked_at` 没有对应索引。
- 按设备删除 `activity_tokens` 缺 `device_id` 索引。
- cleanup 按 Job 删除 `transactional_outbox.aggregate_id` 缺对应索引。
- `agent_tool_requests.expires_at` 当前主要用于排序和业务过期判断，没有直接按 expires_at 删除的 SQL；
  不应仅凭字段名加索引。先对 pending-tool join + order 做 `EXPLAIN (ANALYZE, BUFFERS)`。
- worker 的 `queued OR expired-running` 查询未必能充分利用当前三列索引，需要在真实基数上比较当前
  索引、两个 partial index 或改写查询，而不是静态猜测。

所有 PostgreSQL 变化只通过新 migration 实施；不修改 `001_initial.sql`。对 UPDATE / DELETE 的
`EXPLAIN ANALYZE` 放在事务中并回滚。

## 2. 0.0.14 实施顺序

### P0-A：先补真实性能场景和 signpost

- [ ] 扩展长流 fixture：有换行段落、20k+ 无换行长段、混合 Markdown 三种输入。
- [ ] fixture 走真实 `assistantTextCompleted` / `completed`、一次持久化和完成态渲染，不再只测永不完成的
  瞬态 buffer。
- [ ] 分开记录 `stream-project`、`stream-scroll`、`stream-to-completed`、Markdown parse、完成态首次布局、
  完成后 Tab 切换和内存。
- [ ] 先录 0.0.13 Release 真机基线，再改代码；每个场景至少三条独立 trace，不能用 Simulator 绝对值。

### P0-B：修复进展快照状态机

- [ ] 用明确的 `idle/loading/loaded/failed` 状态替代 `.empty + try?`；失败时显示可重试错误，不让页面
  永久空白。
- [ ] 每次 load 携带目标 revision；完成后若 `currentKey != targetKey`，立即合并触发下一次加载，不能把
  旧结果标成最新。
- [ ] 相关保存发生在页面可见且 load in-flight 时只合并一次 follow-up，不制造查询风暴。
- [ ] 建立 container 级、按实体过滤的失效信号，覆盖 main context 与后台 ModelActor/context。
- [ ] 测试：首载错误、首载期间插入数据、连续多次保存、后台 context 保存、取消、保持在当前 Tab、不依赖
  Tab 重建的恢复。

### P0-C：消除流式长度增长和完成时悬崖

- [ ] 把「最多 256 字符可变尾部」变成可执行不变量，并修改当前反向单测。候选实现必须保持原始文本
  完全一致，不得为了分块插入可见换行。
- [ ] 在真机上比较“语义块 + 有界 inline 尾部”和增量 TextKit/平台文本存储；以 trace 选择实现，避免
  仅凭 SwiftUI 结构猜测。
- [ ] 完成态 Markdown 纯解析移出 MainActor；缓存写入和 UI 状态提交回主线程。
- [ ] 单条完成回复内部按 block lazy / progressive materialization，或先保留稳定流式块再渐进升级可见
  Markdown；禁止一次构造全部完成态 block。
- [ ] 完成态首帧准备好后再释放 live buffer、取消滚底任务，避免同一帧同时做全文合并、JSON 编码、
  SwiftData save、Markdown parse 和全量布局。
- [ ] 保留“delta 不写 SwiftData”的正确边界，并验证完成/失败/取消只进行必要的一次正文提交。

### P1：收窄 SwiftData 查询

- [ ] 去重查询先下推日期/source/业务条件，并加小上限；fingerprint 只处理候选集。
- [ ] Job claim 下推 data space / 状态 / retry 条件，保留严格 FIFO；用测试覆盖前序 waiting job 是否阻塞
  后续 job 的既有产品语义。
- [ ] HealthKit 只查询当前增量涉及的 external IDs，或在 schema 决策后建立复合唯一身份。
- [ ] 以 10k / 50k 虚构记录压测上述热查询，记录返回行数、物化对象数、p50/p95 和取消行为。
- [ ] 做出 iOS 17 / iOS 18 决策；选择路径 B 才实施 SwiftData `#Index`，并同步数据库结构文档。

### P1：验证并调整 PostgreSQL 索引

- [ ] 配置隔离的 `SOMA_TEST_DATABASE_URL`，让当前被跳过的 PostgreSQL 集成测试真正运行。
- [ ] 用接近生产基数的虚构数据对 claim、event cursor、pending tool、cleanup、device erase 录制
  `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。
- [ ] 只为有计划收益的查询创建新 migration；删除重复 event cursor index。
- [ ] 运行 `make db-migrate-status`、`make db-migrate`、Server 测试和 migration 重放测试。

## 3. 验收边界

### 流式与完成态

- 35 秒有换行流、20k+ 无换行流和混合 Markdown 完成路径均无 `>100 ms` 主线程停顿。
- 可重复 SwiftUI `body` 热点 `<1 ms`，滚动 hitch `<1%`；无换行流的每次增量成本不随全文长度线性上升。
- `stream-to-completed` 不出现单帧全量 Markdown 构建；完成后 30 轮四 Tab p95 继续 `<100 ms`。
- 连续三条长回复后 RSS / dirty memory 不单调增长；若增长，追加 Allocations 和 memgraph 证据。
- 完成态文字、Markdown、选择、VoiceOver 和持久化重放与原文本完全一致。

### 进展

- 首载失败有明确错误和重试；页面保持打开时数据保存能自动出现，不依赖重新切 Tab。
- load in-flight 期间任意次数相关保存，最终 snapshot key 必须等于最新 revision。
- 非相关 Agent Event / Trace 保存不触发 Insights 查询；相关后台 context 保存必须触发一次合并刷新。

### 数据库

- 所有点查、分页、去重和 claim 返回结果与改造前一致；不得因 `fetchLimit` 改变 FIFO、幂等或数据真值。
- 压力数据上不再物化整张 Workout / Meal / Body / Job 表。
- 每个新增索引都有对应热查询、before/after 计划与耗时证据；无收益或重复索引不保留。
- SwiftData schema 变化验证现有 store 打开、个人/演示空间、备份恢复；PostgreSQL 只向前 migration。

### 交付

- `make check`、`make verify`、`make perf-check` 全部通过。
- Release 真机 Time Profiler、SwiftUI、Animation Hitches、Allocations 分别采样；Simulator 只做功能预检。
- 分别报告代码、自动门禁、真机安装、真机 trace、人工交互、CI、tag / GitHub Release / TestFlight 状态。

## 4. 明确不做

- 不用提高流式节流间隔、截断历史、关闭动画或销毁 Tab 状态掩盖实际工作。
- 不把用户业务数据复制到服务端换取查询速度。
- 不直接修改 SwiftData 私有 SQLite schema，也不在没有 query plan 的情况下批量加索引。
- 不把 0.0.13 的行为保持重构再次演变成 DDD / repository / use-case 层迁移。
